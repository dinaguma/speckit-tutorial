# Blog API Constitution

## Core Principles

### I. Security First
- すべての機能実装は「安全性」を最優先で判断する。
- 入力値は必ずバリデーションし、SQLインジェクション、XSS、CSRF、認可不備を防止する。
- 認証はJWTを標準とし、署名アルゴリズム、失効戦略、有効期限、リフレッシュ手順を明確に定義する。
- 秘密情報（JWTシークレット、DB接続情報）は環境変数で管理し、リポジトリに含めない。
- 依存ライブラリの脆弱性監視を継続し、重大脆弱性は最優先で修正する。

### II. RESTful and Versioned API
- APIはRESTful設計原則に準拠し、リソース指向のURI設計を行う。
- APIバージョニングは必須とし、v1を `/api/v1` プレフィックスで公開する。
- 破壊的変更は同一バージョンに混在させず、新バージョンで提供する。
- エンドポイント命名、HTTPメソッド、レスポンス構造は一貫性を維持する。

### III. Clear Error Handling
- 例外は握りつぶさず、アプリケーション層で統一ハンドラに集約する。
- エラーレスポンスは機械可読かつ人間可読な形式で返却し、最小限の原因特定情報を含める。
- 内部実装や秘密情報（スタックトレース、SQL詳細、鍵情報）は本番レスポンスに含めない。
- 適切なHTTPステータスコードを厳守する。
- バリデーションエラーは `400`、認証失敗は `401`、認可失敗は `403`、未検出は `404`、競合は `409`、予期しない障害は `500` を基本とする。

### IV. Documentation as a Deliverable
- OpenAPI（Swagger）ドキュメントは必須成果物とし、実装と同時に更新する。
- すべての公開エンドポイントに対して、リクエスト、レスポンス、エラー仕様、認証要件を明記する。
- 仕様変更時はドキュメントを先行または同時更新し、実装と乖離させない。
- ドキュメントは開発・QA・運用の共通契約として扱う。

### V. Test Quality Gate
- テストカバレッジ80%以上を品質ゲートとし、未達の場合はマージしない。
- 単体テスト、統合テスト、主要APIのE2E観点を組み合わせ、正常系と異常系を検証する。
- 認証・認可、入力バリデーション、エラーハンドリング、DBアクセスは重点テスト対象とする。
- CIで自動テストを実行し、再現可能な失敗を最優先で解消する。

## Technical Standards
- バックエンドはNode.js + Express.jsを標準スタックとする。
- データベースは開発環境でSQLite、本番環境でPostgreSQLを想定し、移行容易性を意識したデータアクセス設計を行う。
- SQL方言差異を吸収するため、クエリ設計とマイグレーション運用に互換性基準を設ける。
- 設定値（ポート、DB、JWT、CORS等）は環境別に分離し、12-Factor Appの原則を尊重する。

## Development Workflow and Quality Gates
- 新規エンドポイント追加時は、設計（OpenAPI）→実装→テストの順で進める。
- Pull Requestでは以下をレビュー観点として必須確認する。
- セキュリティ要件を満たしていること。
- HTTPステータスコードとエラーフォーマットが規約に一致していること。
- `/api/v1` 配下で一貫したREST設計になっていること。
- OpenAPI仕様と実装に差分がないこと。
- テストカバレッジ80%以上を維持していること。

## Governance
- 本憲法はブログAPI開発における最上位ルールであり、他の実装慣行より優先される。
- 例外運用は、理由・影響範囲・期限・代替策を文書化し、レビュー承認を必須とする。
- 本憲法の改訂は、変更理由と移行方針を伴うPull Requestで実施する。
- すべての仕様書、計画書、タスクは本憲法への準拠確認を含める。
